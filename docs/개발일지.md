# 🚀 AI 거시경제 리서치 파이프라인 개발 일지

## 1단계: API 속도 한계 극복 및 병렬 처리 도입

* **개발 방향:** 여러 기사를 순차적으로 분석하는 데 걸리는 긴 대기 시간을 단축.
* **마주한 문제:** 에이전트 B(분석가)가 3개의 기사를 하나씩 읽고 요약하느라 전체 파이프라인의 병목 현상 발생.
* **해결 방안:** 파이썬의 `concurrent.futures.ThreadPoolExecutor`를 도입하여 **멀티 스레딩(Multi-Threading)** 구현. 3개의 API 요청을 동시에 쏘아 올려 작업 시간을 3분의 1로 단축함.

## 2단계: Rate Limit(속도 제한) 방어 및 자동화 기반 마련

* **개발 방향:** 1분당 5회(RPM)라는 무료 API의 타이트한 한도를 우회하면서 시스템의 안정성 확보.
* **마주한 문제:** 병렬 처리와 편집장(Agent C) 호출이 겹치면 순간적으로 5 RPM을 초과하여 구글 서버에서 `429 (Too Many Requests)` 에러를 발생시킬 위험 존재.
* **해결 방안:**
1. `smart_gemini_call`이라는 래퍼(Wrapper) 함수를 만들어 에러를 감지하는 로직 구현.
2. 병렬 처리 직후 파이썬 코드 단에 `time.sleep(65)` 형태의 Safety Sleep(안전 대기)을 강제로 주입하여 1분 카운트 버퍼를 초기화함.



## 3단계: 블랙 스완 대응 및 스케줄링 고도화

* **개발 방향:** 매일 같은 키워드("금리")만 검색하는 하드코딩을 탈피하고, 하루 3회 자동 실행(Crontab)에 맞춘 유연한 시스템 설계.
* **마주한 문제:** 고정 키워드로는 예상치 못한 경제 이슈(블랙 스완)를 놓치며, 하루 여러 번 실행 시 출력 파일명이 덮어씌워짐(Overwrite).
* **해결 방안:**
1. 검색어를 "경제 주식" 등 광범위하게 열어두고, 데스크(Agent A)가 그날의 '핵심 키워드'를 스스로 도출(Dynamic Keyword)하도록 프롬프트 수정.
2. 파일명에 `YYYY-MM-DD_HHMM` 형태의 타임스탬프를 부여하여 덮어쓰기 원천 차단.



## 4단계: LLM 비용(Token) 제로화 및 거시 지표 결합

* **개발 방향:** 리포트의 전문성을 높이기 위해 수치 데이터를 결합하되, LLM의 토큰 낭비를 최소화.
* **마주한 문제:** 경제 지표를 파악하기 위해 LLM에게 숫자 관련 뉴스를 읽히는 것은 비효율적이고 환각(Hallucination) 위험이 큼.
* **해결 방안:** 파이썬 `yfinance` 라이브러리를 활용한 **Data Collector** 추가. LLM을 거치지 않고 실시간 환율, 금리, S&P 500 지수 등을 직접 크롤링하여 편집장(Agent C)의 프롬프트에 직접 주입(Injection)함.

## 5단계: 서버 과부하(503) 대응 및 모델 Fallback 시스템

* **개발 방향:** 외부 API 서버의 장애 상황에서도 파이프라인이 멈추지 않는 극강의 생명력 부여.
* **마주한 문제:** 내 로직의 잘못(429)이 아닌 구글 서버 자체의 트래픽 폭주로 인한 `503 (Service Unavailable)` 에러 발생으로 프로그램 강제 종료.
* **해결 방안:** 에러 캐치 로직을 고도화하여 503 에러 시 10초 대기 후 재시도하도록 설정. 2회 실패 시 미련 없이 `gemini-3.6-flash` 등 하위 대체 모델로 스위칭(Fallback)하는 무적의 재시도 루틴 완성.

## 6단계: State(기억) 부여를 통한 연속적 맥락 분석

* **개발 방향:** 어제와 오늘의 경제 흐름을 연결하는 진짜 '전문가' 수준의 연속적 분석 구현.
* **마주한 문제:** 에이전트들이 단기 기억 상실증처럼 매일 뉴스를 '처음 보는 것처럼' 분석함. LangGraph를 쓰기엔 무료 API 한도(RPD 20) 소모가 너무 큼.
* **해결 방안:** 파이썬 내장 `SQLite3`를 활용해 초경량 로컬 DB(`memory.py`) 구축. 매일의 요약을 저장하고, 분석 시 최근 5일 치의 기억을 프롬프트에 주입(RAG 형태)하여 트렌드의 변곡점을 추론하도록 고도화.

## 7단계: 모델 티어링(Model Tiering)을 통한 자원 한계 돌파

* **개발 방향:** 일 20회인 Heavy 모델의 한도를 아끼고, 입력 토큰(TPM) 여유분을 활용해 일간 종합 리포트로 스케일업.
* **마주한 문제:** 단순 기사 선별이나 조판 작업에도 값비싼 Heavy 모델의 할당량을 낭비하고 있었음.
* **해결 방안:**
1. 역할에 따라 Heavy 모델(분석)과 Lite 모델(선별, 조판)을 분리 배정하는 **모델 라우팅(Model Routing)** 적용.
2. 모델별로 한도(RPM)가 따로 돈다는 점을 파악하여 불필요했던 65초 대기 시간을 삭제하고, 기사 수집 풀을 50개(선별 8개)로 대폭 확장함.


## 8단계: Lite 모델을 레버리지한 LLM-as-a-Judge 및 전처리 도입

* **개발 방향:** 남아도는 Lite 모델의 일일 한도(500회)와 토큰 창(250K)을 쥐어짜 내어 리포트의 무결점 달성.
* **마주한 문제:** Heavy 모델이 노이즈 텍스트를 읽고 번역하느라 지능이 분산됨. 편집장이 가끔 마크다운 양식을 틀림.
* **해결 방안:**
1. **Agent E (전처리):** Lite 모델이 원문을 한국어로 완벽히 번역하고 노이즈를 제거하여 Heavy 모델에게 팩트만 전달.
2. **Agent D (검수자):** 완성된 리포트를 Lite 모델이 채점하고, 불합격 시 수정 지시(Feedback)를 내려 다시 쓰게 만드는 **자가 수정(Self-Correction) 무한 루프** 구축.


## 9단계: 배포 및 운영 안정화 (CI/CD 관점)

* **개발 방향:** 파일 시스템 에러 방지 및 개인화된 알림 시스템 구축.
* **마주한 문제:** LLM이 생성한 키워드에 슬래시(`/`) 등 특수문자가 포함되어 리눅스 파일 저장 시 `FileNotFound` 에러 발생. 해외 경제 뉴스 소스 부족.
* **해결 방안:**
1. 정규표현식(`re.sub`)을 통해 파일명 특수문자를 언더바(`_`)로 안전하게 치환(Sanitize).
2. WSJ, Yahoo Finance 등 RSS 소스를 다각화.
3. `requests`를 이용해 **Discord Webhook** 알림 모듈(`notifier.py`)을 연동하고, Crontab을 주 5일(1-5)로 설정하여 최종 프로덕션(Production) 레벨 완성.

## 향후 벡터 DB로의 마이그레이션(Migration) 시나리오
1. 기존 데이터 추출 (Extract)
기존에 만든 economy_memory.db 파일에서 SELECT * FROM daily_memory로 그동안 쌓인 모든 요약 리포트를 파이썬으로 한 번에 불러옵니다.

2. 텍스트 임베딩 (Embedding)
불러온 텍스트들을 AI가 이해할 수 있는 '숫자 좌표(벡터)'로 변환합니다. 이때도 구글 Gemini API가 제공하는 무료 임베딩 모델(예: text-embedding-004)을 사용하여 텍스트를 좌표값으로 바꿉니다.

3. 벡터 DB에 밀어 넣기 (Load)
변환된 좌표와 원본 텍스트를 묶어서 라즈베리파이에서도 가볍게 돌아가는 로컬 벡터 DB(예: ChromaDB 또는 FAISS)에 통째로 밀어 넣습니다.

### 아키텍처는 어떻게 달라지는가
이 마이그레이션이 끝나고 나면, 현재 파이프라인의 memory.py 역할이 완전히 새로운 차원으로 바뀝니다.

현재 방식 (SQL 조회):
"무조건 최근 5일 치 기록만 가져와서 줘." (ORDER BY date DESC LIMIT 5)

미래의 방식 (의미 검색 RAG):
오늘 수집된 기사가 '중동 전쟁으로 인한 유가 급등'에 관한 것이라면, 시스템이 벡터 DB에 이렇게 질문합니다.
"과거 3년 치 리포트 중에서, 오늘처럼 '지정학적 리스크와 유가 폭등'이 발생했던 가장 유사한 상황 3개만 찾아서 가져와."

그러면 에이전트 B(분석가)는 과거에 유사한 위기가 닥쳤을 때 시장이 어떻게 반응했는지 정확한 선례를 바탕으로, "2024년 중동 분쟁 당시와 유사한 패턴을 보이고 있으며, 당시 방산/정유 섹터가 급등했던 점을 고려할 때..." 라는 통찰력을 발휘하게 됩니다.

### 국내 뉴스 수집기 점검
국내 뉴스가 검색어 관련순으로만 수집을 하다보니 가장 최신 글을 안가져오는 경향을 발견
관련순으로 수집 후 최근 글들로 필터링하여 컨텍스트로 넘김

### LLM 컨텍스트 유실 현상 발견
결과 노트에 '데스트 시황 코멘트'아 누락됨을 확인
이에 `cron.log`를 확인해보니 검수자가 재작성을 지시하고 편집장 에이전트가 이를 누락하고 재작성을 진행하는 컨텍스트 유실 현상 발생
이를 방지하기 위해 고정된 템플릿에 본문 내용을 코드에서 결합하는 방식으로 수정하여 템플릿에서 벗어나게 되는 현상을 방지

### 아키텍처 변경
기존의 LLM 병렬요청을 통해 시간 단축의 효과를 누리려고 했으나 무료버전의 한계인지 병렬 요청시 문제가 생길 수 있음을 인지함.
따라서 수행시간의 단축 효과가 별로 의미가 없기 때문에 병렬 처리에서 직렬 처리로 로직을 변경함.
